# Evidence collection tools

The research driver is `tools/research.py`. It **selects paper-specific research
inputs and runs existing tools**; it does not parse Lean, generate a second
source-result inventory, infer historical attribution, or maintain a new CI gate.
Its output lives under `build/what-it-takes-dk/`, not in the maintained census.

## First run: full-scope sine-theta pilot

Run these commands **sequentially** from the repository root:

```bash
cd ~/code/aiq-dkps-formalization
python3 papers/what_it_takes_to_prove_davis_kahan/tools/research.py plan sine_theta
python3 papers/what_it_takes_to_prove_davis_kahan/tools/research.py collect sine_theta --run
```

The `plan` command prints the complete commands without executing them.
Running `collect` with `--run` then:

1. Snapshots the current Git revision, selected source/census/toolchain input
   hashes, and exact theorem roots. Optionally, `--paper-pdf` records a local
   original-PDF digest; **it never copies or redistributes the PDF**.
2. Runs `lake exe cache get` **before** building the source and finite-dimensional
   comparison modules.
3. Runs the existing Davis--Kahan source-census check.
4. Invokes the installed `leanq graph-index`, with the configured import roots;
   saves a case-specific elaborated semantic index.
5. Uses `leanq graph-slice` for the full-scope, rectangular, and finite routes;
   generates statement-closure JSON. A separate generated Lean importer runs
   `#check` and `#print axioms` for all roots, including the opt-in small-angle result.
6. Uses `aiq-lean alignment html` to build a one-result source-to-Lean review
   page, then creates an annotated Markdown evidence packet and an explicitly
   **provisional mathematical** Mermaid diagram.

Outputs include:

| File | Use |
| --- | --- |
| `build/what-it-takes-dk/sine_theta/snapshot.json` | Commit and input identifiers; digest of user-provided primary source when supplied |
| `.../semantic-index.json` | Elaborator-backed evidence, generated by `leanq` |
| `.../slices/{full,rectangular,finite}.json` | Three saved named-declaration closures; `leanq` marks type/proof dependencies where available |
| `.../statements/*.json` | Elaborated theorem types and relevant definition closure |
| `.../source_axiom_audit.lean` and `.txt` | Generated `#check` and `#print axioms` for every root and captured Lean output |
| `.../source-alignment.html` | Source text, correspondence review, Lean statement and dependency inspection |
| `.../evidence_packet.md` | Unresolved mathematical and historical obligations, joined to the exact named formal candidates |
| `.../proposed_mathematical_route.mmd` | Five-step mathematical argument, **not** inferred from code edges |
| `.../executed_commands.json`, `.../logs/` | Executed commands, exit codes, and complete logs |

The script requires the installed `leanq` and `aiq-lean` commands from
`aiq-lean-formalization-tools`. Install that project as described in `dev/README.md`
if the CLIs are not on PATH. The case-specific index is deliberately separate
from `build/leanq/project-semantic-graph.json`; other research and review tasks
are unaffected.

To regenerate the Markdown report after editing the **human evidence** fields,
without running Lean again:

```bash
python3 papers/what_it_takes_to_prove_davis_kahan/tools/research.py report sine_theta
```

To rerun all slices using the existing case index, after checking the repository
revision and all relevant Lean sources are unchanged:

```bash
python3 papers/what_it_takes_to_prove_davis_kahan/tools/research.py collect sine_theta --reuse-index --run
```

`--reuse-index` is an explicit scientific decision. The tool hashes selected
inputs, but does **not** prove graph freshness across all transitive Lean
sources or external library changes. Recreate the index whenever the relevant
Lean environment changes. Never cite an index as current without verifying
its provenance.

## Curating evidence: a disciplined editing loop

The checked-in configuration files are **research questions**, not a second
verification status register:

- `data/cases.json` chooses the exact source result ID, source-facing theorem,
  independent comparison roots, hypothesized mathematical steps, and named
  dependency probes. If a declaration is renamed, reconcile it against the
  maintained source inventory; **do not** pick a similarly named replacement
  automatically.
- `data/research_questions.json` records RQ1--RQ6 and H1--H4. Human investigators
  update the hypothesis status only after checking the mathematical evidence.
- `data/history_claims.csv` records a proposed historical relationship, the
  locator in Davis--Kahan (1970), the primary antecedent page/theorem, and the
  relationship category. `to_check` entries are **not** confirmed priority or
  influence assertions.
- `data/route_comparisons.csv` records competing proof routes and their **exact
  hypotheses and conclusions**. A graph can help find candidate lemmas; it
  cannot establish that an alternative proof is equivalent or that a given
  theory is logically indispensable.

For a history row to support a paper claim, supply the original source locator,
the antecedent locator, the precise mathematical relationship, and a review
note. Distinguished relationship categories include `explicitly_cited_1970`,
`candidate_predecessor`, `retrospective_connection`, and
`later_reformulation`. Never convert an earlier publication date alone into a
historical-influence arrow.

For a route comparison to count, present both derivations or cite full proofs,
state where domain hypotheses are consumed, and compare scalar fields,
infinite-dimensional scope, gap alternatives, ideal-membership constraints,
and constants. A `graph-slice` contains **declaration reachability in a
particular Lean implementation**, not a minimum basis of mathematical ideas.

The driver does not update `dev/*.json`, do proof search, rewrite Lean code, or
change the existing journal manuscript. The historic 1970 paper is not added
as a repository asset; store a file digest and scholarly locator instead.

## Interpretation constraints

- **Observed in closure**: a named constant is present in a saved elaborated
  dependency slice of the selected theorem. This supports a claim about the
  implementation at the indexed revision, subject to the indexer's limitations.
- **Not observed in closure**: no such named constant is visible. It is *not* a
  proof of the mathematical independence of the theorem or a particular
  argument; opaque and proof-internal dependencies can be missing.
- **Provisional arrow** in `proposed_mathematical_route.mmd`: an author's proposed
  mathematical reduction, needing a complete proof and source alignment.
- **Historical arrow**: add one to manuscript figures only after reading and
  identifying the relevant primary source and relationship. The driver never
  generates historical arrows.
- **Formal verification of old results**: use the authoritative existing
  inventories and Lean build. These tools do not change the accepted verification
  state of the original 29 results or the verified small-angle extension.
